# Каркас интеграции v20

## База и точка расширения

Исследован `adventure-v19-play-2.html`: автономный HTML с одним classic-script.
В нём модули склеены по маркерам `// ---- js/<name>.js ----`. Последний
`main.js` создаёт `window.game` и запускает RAF. Расширения вставляются
непосредственно перед этим маркером, после `audio-hooks.js`: видны все
лексические `const`/`class` v19, а экземпляр игры ещё не создан.

`tools/v20-compose.js` не меняет исходник. Он читает HTML либо gzip, проверяет
якорь, структуру v19, контрольную сумму при её указании, зависимости и синтаксис
как каждого патча, так и итогового script. Он запрещает повторную компоновку,
HTML-терминаторы script в патчах и запись поверх входных файлов. Выход пишется
атомарно; `--check` выполняет проверки без записи. Родительский каталог выхода
должен существовать. Компоновщик исполняется в Node без сторонних зависимостей;
патчи считаются доверенным кодом разработчика, а не безопасным пользовательским вводом.

## Манифест и запуск

Готовый `tools/v20-manifest.json` закрепляет SHA базы и порядок патчей:

```json
{
  "version": 1,
  "patches": [
    {"id": "storage", "file": "v20-storage.js"},
    {"id": "enemies", "file": "v20-enemies.js", "after": ["storage"]},
    {"id": "maps", "file": "v20-maps.js", "after": ["enemies"]},
    {"id": "design", "file": "v20-design.js", "after": ["maps"]},
    {"id": "heroes", "file": "v20-heroes.js", "after": ["design"]}
  ]
}
```

Это предлагаемый порядок; согласуйте реальные зависимости с авторами патчей.
`after` проверяет уже пройденные записи, автоматической перестановки нет.
Пути файлов разрешаются относительно манифеста. Для воспроизводимости добавьте
`baseSha256` из первого отчёта (SHA распакованного HTML). Отчёт содержит также
SHA каждого патча, итогового HTML и его размер; временных меток нет.

```sh
node tools/v20-compose.js --base /path/to/adventure-v19-play-2.html --manifest tools/v20-manifest.json --out /tmp/adventure-v20-candidate.html
node tools/v20-compose.js --base adventure-v19-play.html.gz --manifest tools/v20-manifest.json --check
```

После загрузки `window.V20Build` содержит метаданные и `installed`: идентификатор
добавляется только после выполнения соответствующего файла. Исключения установки
не подавляются. Компоновка не доказывает корректность игры в браузере.

Финальный design-патч загружает два PNG через `../assets/v20/`: файл кандидата
размещается в `/adventure-v20/`, изображения — в `/assets/v20/`. Копируйте оба
`seam-crab.png` и `ceramic-observatory-floor.png` при публикации. Сам компоновщик
не копирует ассеты; кандидат с этим патчем уже не полностью автономен. Относительный
URL должен разрешаться относительно документа игры, в том числе при gzip loader.
При прямом открытии файла воспроизведите эту структуру каталогов.

## Контракт патчей

- Обычный JS внутри IIFE, без ES imports, внешних CDN и повторного `startGame`.
- `HEROES`, `HERO_BY_ID`, `SKILLS`, `MONSTERS`, `BOSSES`, `Game`, `Player`,
  `Renderer`, `UI`, `SeamlessFloor`, `ActorMotion` доступны напрямую. Большинство
  объявлено через `const`/`class`, поэтому `window.Game` может быть отсутствующим.
- Методы оборачивать с сохранением `this`, аргументов и результата; старый метод
  вызывать ровно один раз, если явно не документирована замена поведения.
- Не переопределять целиком цепочки update/render: v19 уже связывает там бой,
  звук, анимацию, сохранения и биомы. У hero/enemy патчей отдельно согласовать
  `updatePlayer`, `updateEnemy`, создание атак и момент применения статистик.
- Не создавать дополнительный RAF. Рисование балансирует `ctx.save/restore`;
  визуальный шум не потребляет RNG генерации уровня. Любой runtime-кэш должен
  быть ограничен по размеру и восстанавливаться после загрузки.

## Совместимость сохранений

Не менять ключи `shadows-undermountain-save-v1`,
`shadows-undermountain-audio-v1`, `RoomRoute.key`.
Первый патч `v20-storage.js` переключает изменяемое свойство `SeamlessFloor.key`
с `undermountain-biomes-v3` на `undermountain-biomes-v20-preview` до создания
Game. Все checkpoint save/resume/menu/pagehide операции v19 читают свойство
динамически, поэтому перехватывать весь Storage.prototype не требуется.
При отсутствии preview-ключа патч один раз копирует старый checkpoint без изменения
исходного значения; штатная загрузка затем проверяет его. Существующее значение,
включая JSON `null` после смерти/завершения, не заменяется старым забегом.
Если чтение или запись запрещены, ключ остаётся изолированным; записи в v19
никогда не используются как fallback. Meta Save остаётся общим по требованию.
Проверка: `node tools/test-v20-storage.js`.
`Game.prototype.saveJourney` имеет явный список сохраняемых полей: добавленное
поле экземпляра не сохраняется автоматически.

Текущий seamless checkpoint имеет `version: 4`; загрузчик принимает 3 и 4,
16 комнат, известные hero/enemy/level IDs, `arenaVersion` 0 или 1. Правила v16
имеют `layoutVersion: 16`, это не номер релиза HTML. Нельзя просто поставить
20: старые валидаторы и условия боя проверяют именно 16. `resumeSeamlessJourney`
восстанавливает карту из seed, levelId, layoutVersion, difficulty, arenaVersion;
затем прикладывает сохранённые координаты сущностей.

Поэтому v19 checkpoint обязан получать прежнюю геометрию. Новая геометрия требует
отдельного маркера, его сериализации, валидации и выбора правильного генератора
при восстановлении и переходе на следующий этаж. Одной обёртки старта недостаточно.
Без такого механизма расширять только визуал или данные, не влияющие на коллизии.
Текущий `v20-maps.js` использует JSON `mapVersion:20` и runtime
`journey.v20MapVersion:20`, сохраняя `layoutVersion:16`; enemies читает этот же
runtime-маркер. Обёртки start/resume/descend устанавливают вариант до генерации.
Существующие IDs не удалять. Отсутствующие новые поля получать из безопасных
значений по умолчанию; не сбрасывать прогресс при ошибке. Новый тип врага в
checkpoint также исключает обещание обратной загрузки этого checkpoint в v19.

## Обязательная проверка кандидата в браузере

1. Поднять HTTP-сервер на отдельном каталоге кандидата. Использовать тестовый
   профиль Chromium/Playwright и копию localStorage, не действующий профиль игрока.
2. Ловить `pageerror` **и** `console.error`: RAF v19 ловит ошибки внутри кадра и
   печатает их в консоль, поэтому только `pageerror` пропустит сломанный игровой цикл.
3. Проверить меню, список героев, обычный старт без `debug`, движение, атаку,
   навыки, паузу, инвентарь, звук и несколько секунд update/render без ошибок.
   Сравнить `V20Build.installed` с порядком манифеста и убедиться в `window.game`.
4. Прогнать каждого героя и каждую главу через явный developer вход
   `?debug=1&map=<levelId>`, включая `ashen` и `citadel`; проверить конечные
   координаты/HP/cooldowns и видимость игровых объектов. Новый уровень не должен
   стартовать автоматически при обычном посещении страницы.
5. На v19 получить живой checkpoint для фиксированного seed. На кандидате
   восстановить его: hero, level, seed, комнаты, позиции, коллизии, предметы,
   таланты и прогресс должны сохраниться. Проверить версии 3/4 и arenaVersion 0/1.
6. Сохранить новый забег v20, перезагрузить страницу, продолжить и перейти этаж.
   Если меняется геометрия, сравнить детерминированные координаты/препятствия до
   и после reload, а также убедиться, что spawn, сундуки и проходы достижимы.
7. Проверить маленький экран, touch, потерю фокуса, сбой localStorage, повреждённый
   checkpoint и отключённую сеть. Записать фактический результат и ограничения.
8. Для волн заполнить все точки появления препятствиями или живыми врагами:
   очередь EncounterDirector не должна навсегда запирать комнату. В баланс-прогоне
   отдельно сравнить Нэму и стрелка по урону, риску сближения и возможности кайта.

10 глав из `WorldTour.order` — start, update, render, save/resume и точное
совпадение геометрии до/после; все 5 героев — базовая атака, 3 умения, 60 update
и render; настоящий checkpoint создан на исходной v19, восстановлен на v20
с идентичными комнатами/коллизиями и без маркера нового генератора. Всё прошло.
Также прошли синтаксис общего script, детерминированность компоновки, отказы
при неверном SHA базы и нарушенной зависимости патчей. Прогон повторён после
добавления нового арта с загрузкой внешних PNG. Изменения патчей требуют повторения.

Этот smoke не доказывает браузерные события, звук, полноту UI, боевой баланс,
поведение насыщенной волны и все исторические checkpoint. Браузерный прогон
обязателен перед публикацией.

Публикация — отдельный шаг после проверки кандидата. Этот каркас не меняет
`index.html`, workflow Pages, v19 gzip и существующие v19 тесты.
